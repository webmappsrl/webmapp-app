# QR code deep link per poi, tappa e cammino

## Cosa cambia

Un link condiviso a questo dominio (es. `https://{appId}.{shard}.webmapp.it/map?track=X`, già generato oggi da `share.service.ts`, ma in generale **qualunque path e query param del sito**) apre l'app nativa direttamente sulla route corrispondente, invece di aprire sempre la versione web. Il meccanismo copre sia il caso "app già installata" (Universal Links su iOS, App Links su Android) sia il fallback naturale "app non installata" (apertura nella PWA in browser, comportamento invariato). Lo scope non è più limitato al path `/map`: l'intero dominio dell'istanza è associato all'app, e il router Angular decide internamente cosa mostrare per ciascun path — esattamente come farebbe aprendo lo stesso URL in un browser.

Questo repo (webmapp-app, principale) è responsabile di:
- Listener nativo `appUrlOpen` (`@capacitor/app`, già dipendenza presente ma mai usato) in `app.component.ts`, con guard basato su `isConfLoaded$` (stesso pattern già esistente in `app.component.ts:82-89` per `checkAppVersion`): copre sia cold start (aspetta che sia `true`) sia warm start (emette subito se già `true`) senza bisogno di attendere una `NavigationEnd`
- Generazione multi-istanza dei file `.well-known/apple-app-site-association` e `.well-known/assetlinks.json` tramite un registro dedicato `deep-links.json` (nuovo, root del repo: bundle id + fingerprint SHA256 Android per ogni istanza) e un nuovo task Gulp `generateWellKnown` che legge **tutte** le entry del registro e produce i due file aggregati — necessario perché tutte le istanze condividono lo stesso dominio wildcard `*.webmapp.it`/stesso deploy fisico (`wm-webapp`, `app.geohub.webmapp.it`): il file `.well-known` è fisicamente unico, non uno per istanza, quindi deve elencare ogni app associata. Deploy del file generato **manuale una tantum** (via scp), da rieseguire solo quando il registro cambia (nuova istanza aggiunta), non ad ogni build/deploy
- Injection, sempre via Gulp, dell'intent-filter Android (`autoVerify="true"`, host = dominio istanza, **nessuna restrizione di path** — matcha l'intero host) nel manifest generato da Capacitor (stesso blocco che oggi gestisce package/MainActivity/permessi, `gulpfile.js:831-883`) e delle entry `com.apple.developer.associated-domains` in un file `.entitlements` iOS (stesso blocco che oggi gestisce `Info.plist`, `gulpfile.js:1489-1669`), con relativo collegamento `CODE_SIGN_ENTITLEMENTS` in `project.pbxproj` (senza questo riferimento il file `.entitlements` non ha alcun effetto lato firma/capability). Lato Apple, `apple-app-site-association` usa `"paths": ["*"]` (sintassi Apple per "gestisci l'intero dominio") — nessuna limitazione a livello di file di verifica

## Perché

Il cliente (tag `ass_cammini_italia`) vuole usare QR code su guide cartacee e cartelli informativi fisici per portare l'utente direttamente nell'app nativa su una traccia o un POI specifico, invece che nella versione web attuale — un'opportunità di visibilità e di engagement legata a materiale stampato già in produzione.

## Requisiti

- [ ] Listener `appUrlOpen` in `app.component.ts` che intercetta l'URL di lancio/risveglio dell'app e lo inoltra al parsing centralizzato in wm-core (vedi overview wm-core)
- [ ] Guard: il deep link viene processato solo dopo che `isConfLoaded$` è `true`, per evitare race condition con il bootstrap dell'app (copre sia cold che warm start con lo stesso codice)
- [ ] Comportamento a warm start identico a quello odierno di un link condiviso aperto ad app già in background: nessuna eccezione per stati come la registrazione GPS in corso
- [ ] Registro `deep-links.json` (root repo) con una entry per istanza (`bundleId`, `androidSha256Fingerprints[]`) — popolato per ora solo con `camminiditalia` (fingerprint reale da ottenere manualmente, non generabile da questo workflow: dipende da come è firmata l'app in Play Store, vedi rischio dedicato)
- [ ] Task Gulp `generateWellKnown` che legge `deep-links.json` e genera `apple-app-site-association` (un `details` per bundle id, `appID` = `{TEAM_ID}.{bundleId}`) + `assetlinks.json` (un `target` per bundle id) in `builds/well-known/`
- [ ] Upload manuale una tantum (via scp) dei due file generati su `app.geohub.webmapp.it/.well-known/` (dominio servito da `wm-webapp`) — da rieseguire solo quando si aggiunge una nuova istanza al registro
- [ ] Injection Gulp dell'intent-filter Android (`autoVerify="true"`, `android:host` = dominio istanza calcolato automaticamente, nessun `pathPrefix`/`path` — matcha qualunque path) nel manifest generato
- [ ] Injection Gulp del file `.entitlements` iOS con `com.apple.developer.associated-domains` = `applinks:{dominio istanza}`, con verifica/injection del riferimento `CODE_SIGN_ENTITLEMENTS` in `project.pbxproj` (o verifica che Capacitor lo colleghi già in automatico per convenzione di nome file — da chiarire in fase di plan)
- [ ] `apple-app-site-association` con `"paths": ["*"]` (tutti i path del dominio, sintassi Apple dedicata — non un semplice wildcard `/*`)
- [ ] Deep link generico: qualunque path e query param dell'URL vengono inoltrati al router (`handleDeepLink()` non è più limitato a `/map`/`track`/`poi`/`layer`/`filter`). Esclusi esplicitamente `ugc_track`/`ugc_poi` (dati personali, non condivisibili via link pubblico), rimossi indipendentemente dal path
- [ ] Se l'id referenziato non esiste (traccia/POI cancellato o non sincronizzato), il comportamento è identico a quello odierno con query param da browser: nessun errore esplicito, nessun redirect (comportamento silenzioso già presente; nel backend non esiste comunque un concetto di contenuto non pubblicato — ogni id valido è già pubblicamente accessibile oggi tramite ricerca/API, quindi il deep link non espone nulla di nuovo)
- [ ] Rollout end-to-end (attivazione capability, test su device reale) limitato all'istanza `camminiditalia` in questo ciclo; il meccanismo resta generico e si estende automaticamente alle altre istanze quando verrà abilitata la relativa capability Apple
- [ ] La injection Gulp (manifest Android, entitlements/pbxproj iOS) va testata contro i manifest/plist reali generati per **tutte** le istanze esistenti (`camminiditalia`, `carg`, `osm2cai`), non solo quella target del rollout — un bug nella regex di injection girerebbe ad ogni build, per qualsiasi istanza, non solo per quella in test
- [ ] Fallback verificato: link aperto su device senza l'app installata continua ad aprire la PWA in browser esattamente come oggi, senza errori

## Rischi

- **DNS/hosting del dominio target non verificato**: il dominio da usare per Universal Links/App Links/`.well-known` è `{appId}.{shardName}.webmapp.it` (es. `1.camminiditalia.webmapp.it`, formula già in `_assignShareLink()`), confermato dall'utente come dominio di produzione corretto — ma un test DNS diretto durante questo workflow non ha trovato un record risolvibile per quell'host. Va verificato che il DNS/hosting sia effettivamente attivo prima del test end-to-end: se non lo è, è un prerequisito infrastrutturale bloccante, indipendente da questa feature
- **Capability Apple Developer Portal**: "Associated Domains" va abilitata manualmente sul Bundle ID di `camminiditalia` prima che l'entitlement abbia effetto — l'utente ha confermato di avere accesso al portale, ma è un passaggio manuale fuori da Gulp/CI da eseguire prima del test end-to-end
- **Verificabilità solo su device reale**: Universal Links/App Links non sono testabili in modo affidabile su simulatore/emulatore — serve un build firmato reale (TestFlight iOS, APK/AAB firmato Android) con reinstallazione dell'app per forzare la riverifica del file `.well-known` da parte del sistema operativo
- **`filter` supportato solo lato `home.component.ts`**: il parametro `filter` non passa dallo `UrlHandlerService.initialize()` centralizzato ma viene letto direttamente dal componente home — va verificato che il flusso deep link raggiunga comunque quel componente con lo stesso query param intatto
- **QR code fisici stampati diventano permanenti**: una volta che i QR vengono stampati su guide cartacee/cartelli e installati sul territorio, un cambio successivo del formato URL (nomi param, path) li rende inutilizzabili senza possibilità di fix software — richiederebbe ristampa fisica. Il formato URL `/map?track=X`/`?poi=X`/`?layer=X` va considerato stabile e pubblico da questo momento in poi
- **Scope ampliato deliberatamente a tutto il dominio (decisione presa in questo ciclo, non un default accidentale)**: qualunque link a `{dominio istanza}` tenta ora di aprire l'app nativa, non solo `/map` — inclusi link a pagine puramente web senza un vero equivalente nell'app (se esistessero, es. una privacy policy pubblicata sullo stesso dominio). Mitigazione: la SPA gestisce comunque qualunque path tramite il router Angular (stesso comportamento di apertura diretta nel browser), quindi non c'è rottura funzionale — l'unico effetto è che si apre l'app invece del browser anche per contenuti che nell'app potrebbero non avere una route dedicata, mostrando l'eventuale fallback/redirect che il router già applica oggi per path non definiti
- **Path/param non testati esplicitamente in questo ciclo**: la copertura end-to-end (checklist di test) resta concentrata su `/map` con `track`/`poi`/`layer`/`filter` — altri path (es. `/favourites`, `/?search=`) sono coperti dal codice generico ma non hanno un test end-to-end dedicato in questo ciclo, da aggiungere quando servirà davvero un caso d'uso su quei path
- **Fingerprint SHA256 Android non calcolabile a priori se l'app usa Play App Signing**: se l'APK distribuito da Play Store è ri-firmato da Google (comportamento di default per le nuove app), il certificato che finisce sui device degli utenti è quello di Google, non quello del keystore di upload in `builds/keys/`. Il fingerprint corretto per `assetlinks.json` va preso da Play Console → "Integrità dell'app", non calcolato da `keytool` sul keystore locale — verificare quale sia il caso per `camminiditalia` prima di popolare `deep-links.json`
- **File `.well-known` fisicamente condiviso tra tutte le istanze**: essendo lo stesso file per ogni sottodominio `*.webmapp.it` (stesso deploy `wm-webapp`), un errore nel registro `deep-links.json` (es. bundle id sbagliato) rischia di rompere la verifica per **tutte** le istanze già configurate, non solo quella appena aggiunta — ogni modifica al registro va verificata (JSON valido, nessuna entry duplicata) prima dell'upload manuale
- **Cache di Google sui Digital Asset Links (~30-40 minuti), non solo cache del device**: verificato in fase di test (device reale, Pixel 9 Pro XL/Android 16) che dopo aver aggiornato `assetlinks.json` con un secondo fingerprint (per un test locale), l'API pubblica di Google (`https://digitalassetlinks.googleapis.com/v1/statements:list?source.web.site=...`) continuava a restituire solo il fingerprint precedente, con un campo `maxAge` di ~2221 secondi (~37 minuti) — la verifica App Links su Android sembra dipendere (almeno in parte) da questa infrastruttura Google, non da un fetch diretto e immediato dal device. Conseguenza pratica: dopo ogni modifica ad `assetlinks.json`, la propagazione reale può richiedere fino a ~40 minuti anche se il file sul server è già aggiornato e raggiungibile — un test immediato dopo l'upload può risultare in un falso negativo. Testare con una build reale da Play Console (che usa il fingerprint già stabilmente cachato) evita questo problema per la maggior parte dei casi

## Out of scope

- Generazione dell'immagine QR code da stampare su guide/cartelli (il cliente chiede solo che il link funzioni una volta scansionato da un lettore QR esterno)
- Custom redirect domains per singoli clienti (es. `sentieri.caiparma.it`)
- Rollout/test end-to-end su istanze diverse da `camminiditalia` in questo ciclo (il meccanismo — registro, task Gulp, injection nativa — è generico e pronto per altre istanze, ma l'attivazione richiede comunque la capability Apple Developer Portal abilitata per ciascun bundle id, e il fingerprint reale di ogni istanza)
- Deep link su contenuti UGC personali (`ugc_track`, `ugc_poi`)
- Gestione d'errore dedicata per id non trovati (eredita il comportamento silenzioso già esistente)
